# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Flutter app for herpetofauna field surveys: record "transects" (survey routes) on a Google Map, drop points for reptile/amphibian findings with one observation record per finding, attach photos to a record, export/share as CSV/KML/KMZ. Targets Android and iOS. Bundle IDs: `rs.antonijevic.herp_tracker` (Android), `rs.antonijevic.herpTracker` (iOS).

The app started as a copy of Bird Tracker (`rs.antonijevic.bird_tracker`) and is published as a separate app — the two share history but nothing else; there is no data migration between them.

## Commands

Flutter is managed by **fvm** — plain `flutter` is not on PATH. Always go through `fvm flutter ...` / `fvm dart ...`, never the SDK path directly.

```bash
fvm flutter pub get
fvm flutter run                 # dev run on connected device
fvm flutter analyze             # lint (flutter_lints defaults)
fvm flutter build ios --no-codesign   # verify iOS compiles
```

`fvm flutter test` runs three files in `test/`: the CSV/KML export contract (`export_roundtrip_test.dart`), the record form (`species_form_test.dart`), and the KMZ/backup archives (`media_archive_test.dart`). The two widget-test files pump `EasyLocalization` inside `tester.runAsync` — without that its translations never load and every `.tr()` comes back as the raw key.

Two things bite when testing anything photo-related: `dart:io` futures never resolve inside `testWidgets`' fake async, so a temp media directory has to be created in `setUpAll` and `MediaService().init(root: …)` pointed at it; and an `Image.file` whose file actually exists starts an image decode the test binding only finishes inside `runAsync`, so `pumpAndSettle` hangs forever if a thumbnail resolves.

### Release builds

- **Android**: `./build_release.sh [--bump]` — cleans, builds obfuscated appbundle, copies to `herp_tracker.aab` at repo root. `--bump` increments patch+build in pubspec.
- **iOS**: `./deploy_ios.sh` — full build + signed export + upload to App Store Connect via API key. **Bumps version by default**; use `--no-bump` if the version was already bumped, `--no-upload` to only produce the .ipa. Requires `ios/deploy.env` (see `ios/deploy.env.example`). The script patches the generated SPM `Package.swift` from iOS 13 → 15 (the project minimum; file_picker alone needs 14) before building — don't "fix" that seemingly redundant sed.

### Launcher icon

Sources live in `launcher_icon/` (outside `assets/`, so they are not bundled into the app): `app_icon.png` is the full-bleed 1024×1024 square used for iOS, the Android legacy icon and the Play listing, `app_icon_foreground.png` is the artwork alone on transparency, pre-padded to 62% of the canvas for the Android adaptive icon's safe zone. Neither may have rounded corners — iOS and Android apply their own mask, so a rounded source leaves white corners. Regenerate the platform sets with `fvm dart run flutter_launcher_icons` after changing either file. That tool does **not** touch the Android splash screen: `android/app/src/main/res/drawable-*/launch_image.png` is a separate set, referenced from `drawable*/launch_background.xml`, and it kept showing the Bird Tracker logo long after the icons were replaced. It carries its own rounded corners — the splash gets no OS mask — and lives in density buckets sized for a 96dp logo (mdpi 96 … xxxhdpi 384); a single copy in bare `drawable/` counts as mdpi and gets scaled up 3× on a modern phone. The iOS `LaunchImage.imageset` is still Flutter's blank 1×1 placeholder, on purpose. The plate colour `#8BBC53` is repeated in `flutter_launcher_icons.yaml` (adaptive background) and lands in `android/app/src/main/res/values/colors.xml`.

Version format in pubspec.yaml is `X.Y.Z+N`; both scripts bump patch and build number together. Apple requires a new build number for every App Store Connect upload.

## Configuration / secrets (not in git)

- **`.env` at repo root** — bundled as a Flutter asset and required at runtime (`main.dart` crashes without it). Keys: `MAPS_API_KEY` (+ optional `MAPS_API_KEY_ANDROID` / `MAPS_API_KEY_IOS` overrides), `PRIVACY_POLICY_URL`. Consumed in three places: Dart via flutter_dotenv, Android via `build.gradle.kts` → manifest placeholder `${mapsApiKey}`, iOS via `AppDelegate.swift` which parses the bundled asset at runtime.
- **`android/key.properties`** — release keystore config for Android signing.
- **`ios/deploy.env`** — App Store Connect API key credentials for deploy_ios.sh.

## Architecture

Single-screen app: `lib/home_page.dart` hosts the Google Map and drives everything else through dialogs/bottom sheets.

- **State**: `lib/service/data_service.dart` — a ChangeNotifier **singleton** exposed through `provider`; holds the active `Transect`, map controller/completer, map type, and SharedPreferences accessors. Widgets call `DataService()` directly (factory returns the singleton) and `notify()` to trigger rebuilds.
- **Persistence**: `lib/service/sembast_service.dart` — sembast NoSQL singleton with a single `transects` store. Models are **manually JSON-serialized** (`toJson`/`fromJson`, no codegen). This replaced Isar; backup/restore lives here too. A backup is a **`.zip`** (`lib/utils/backup_utils.dart`): `herp_tracker_backup.json` at the root — byte-identical to the old plain-JSON backup — plus `media/` with the record photos. It is written and read with `ZipFileEncoder` / `decodeStream`, streaming photo bytes straight between the media directory and the archive — never buffer a whole archive, a season of field photos is hundreds of megabytes. Restore still accepts a bare `.json` so older backups keep working, and it is destructive by design: it wipes the store and then sweeps media files no restored record references.
- **Models** (`lib/model/`): `Transect` (route with start/end, name) → `points` (recorded track) + `markers` (`Placemark` findings) → `Species` records. `Transect` owns the CSV export; `lib/utils/kml_utils.dart` owns KML and `lib/utils/kmz_utils.dart` the KMZ wrapper around it.
- **Record fields** come from the survey data dictionary ("Vrste za aplikaciju.xlsx" at the repo root). The enumerated ones (development stage, sex, data type, collection method, habitat, water bed, abundance) live in `lib/configuration/field_options.dart` as enums; the **enum `name` is what gets persisted and exported in machine payloads**, while the label always goes through `.tr()` (`optionLabel()` maps a value to its key). The species catalog is a hardcoded list of 50 Latin names in `lib/configuration/species.dart`, each also a key under `species.*` in the translations — reached through `speciesLabel()`/`speciesKey()` in that same file, never by interpolating the name into the key by hand. easy_localization walks a key as a **path**, splitting on `.`, so `species.Pelophylax kl. esculentus` resolved to nothing and rendered as the raw key; the helper drops dots from the key, and the catalog keeps the real name, which is what gets persisted and exported. A test in `species_form_test.dart` asserts every catalog entry resolves, so the next name carrying an abbreviation fails loudly.
- **Automatic fields**: `Species.observedAt` (both the "Datum" and "Datum posmatranja" export columns) and the point's `latitude`/`longitude`/`altitude`/`accuracy` are captured silently — they deliberately have **no inputs** in `SpeciesForm`. Altitude and accuracy are read off `LocationData` in `_createNewMarker` (`home_page.dart`).
- **Export formats**: CSV column order matches the spreadsheet, headers and option labels follow the app language, and the file is written as UTF-8 **with BOM** (Serbian diacritics + Excel). The column set lives once, in `kRecordColumnKeys` + `Placemark.exportValues` (`model/placemark.dart`); CSV and the KML balloon both build from it, so a new record field reaches both. Transect name, point number and the photo list sit outside that list because each export places them differently. KML carries the records as JSON in each placemark's `<ExtendedData>` — that payload, not the human-readable `<description>`, is what re-import reads, so any new record field round-trips as soon as it is in `toJson`. It sits in a **namespaced** `<herp:records>` (`kHerpNamespace`) because a plain `<Data name="records">` is what viewers render as a name/value table, and they printed the raw JSON at the user; KML 2.2 says renderers must ignore foreign-namespaced ExtendedData. `_readRecords` still falls back to the old `<Data name="records">`, or every KML already shared with a colleague would stop importing. Beside it the same ExtendedData carries **one plain `<Data>` per field** — that table *is* the balloon, since a KML reader has no other way to show a record, and `<description>` is only a one-line summary. Both halves are needed: the rows lose the enum names and the exact timestamps, the payload is unreadable. Rows are numbered (`1. `, `2. `) when a point holds several records, or the table would repeat "Species" with nothing to tell the rows apart, and a blank field still gets an empty row rather than being dropped — the viewer shows "No value", which is information. Do **not** put a `<BalloonStyle>` on `markerPlacemark`: `$[description]` hides that table. `Transect.shareKML` emits a **KMZ** (`lib/utils/kmz_utils.dart`) whenever a record photo is on disk and a plain `.kml` otherwise; a KMZ is a zip of `doc.kml` plus `files/`, and only then does `generateKML(photos: …)` swap the placemark description for CDATA HTML with `<img src="files/…">`. That argument is the exact list the archive bundles, so a record naming a photo whose file has gone missing keeps the name in `ExtendedData` — losing it would erase what was photographed — but gets no `<img>` and therefore no broken image in Google Earth. `Transect.hasPhotos` answers from memory alone because the history list calls it from an item builder every frame; `KMZUtils.availablePhotos` is the one that stats the disk, once, in `shareKML`. Import (`showImportDialog`) accepts both, and decides which by **sniffing the zip magic**, never by the extension: share targets rename attachments, and one export came back named `Transect 30.08.2026 as KMZ` with no extension and two stray directories from the `dd/MM/yyyy` in its share subject. That subject and every export file name now go through `sanitizeFileName` (`file_utils.dart`) — the transect name is free text and lands in both. The picker uses `FileType.any` plus its own check rather than `FileType.custom`, because that maps extensions through Android's `MimeTypeMap`, which knows neither `kml` nor `kmz` and greys the files out. The `<img src="files/…">` balloon images only render in Google **Earth Pro** (desktop); the **web** builds of both Earth and My Maps parse the tags but never resolve a path into the archive, so photos read as broken there. Nothing in the KMZ is wrong when that happens — the archive was verified entry by entry — and the photo *names* are in the data table regardless, which is what the field team actually needs.
- **Photos** (`lib/service/media_service.dart`, strip UI in `lib/widgets/photo_strip.dart`): a record may carry several. Each one is stored twice — the canonical copy under `<appDocuments>/media`, which every thumbnail and every export reads, and a user-visible copy in the "Herp Tracker" gallery album via `gal`. A failed gallery write is not fatal, only the shortcut in Photos is lost. `Species.photos` holds **file names, never paths**: the iOS app container path changes between installs, so a persisted path would break. Photos hit the disk before the record exists, so `SpeciesForm` reconciles on save (files it no longer lists are deleted) and on dispose (files added and then abandoned are deleted) — never at the moment the user taps the ×, or cancelling would gut a saved record. The gallery copy is never deleted, the way a camera app behaves.
- **Deleting photos**: only the form deletes files on its own, and only ones no saved record ever owned. Deleting a transect, a point or a record goes through `showDeleteWithPhotosDialog` (`ux_builder.dart`), which adds an opt-in checkbox — **off by default** — for the photos that delete would orphan; without it the files stay. The checkbox copy says photos taken in the app survive in the gallery album but imported ones do not, and that is literally true: `MediaService.writeBytes`, the path a KMZ import and a backup restore take, never pushes to the gallery, so there is no second copy to fall back on. Restore is the one place that still sweeps photos without asking, which is in character since it replaces the whole database anyway.
- **UI helpers**: `lib/utils/ux_builder.dart` — global dialogs/snackbars/bottom sheets using `context_holder` (`ContextHolder.currentContext`), so no BuildContext threading. All user-facing strings go through easy_localization `.tr()`.
- **Map camera**: the camera follows the user only while the app is `resumed` (`_appVisible`, from `WidgetsBindingObserver` in `home_page.dart`); points are still recorded and drawn on the next resume. Updates keep arriving every second from the foreground service with the screen off, and animating the paused, surface-less MapView on each one feeds the Maps renderer NaN targets — `IllegalArgumentException: NaN is not a valid value: (NaN,NaN)` on the render thread, uncatchable from Dart because it is not thrown inside a Pigeon handler. That, and the location crash below, were the two production crashes of Bird Tracker 1.0.16; the same code was here, so both fixes were ported over. `_followCamera` also skips a repeat of the last target (distanceFilter is 0) and any non-finite zoom or coordinate. Coordinates are validated on every way in (`geo_utils.dart`: `isFiniteLatLng`, `finiteOrNull`): `double.parse('NaN')` succeeds in Dart, so KML import, `Point.fromJson`/`Placemark.fromJson` and `goToFirst` drop what the map could not place instead of handing it over.
- **Location**: uses the `location` package (10.x — not geolocator/permission_handler; Play Console's crash "SDK provider note" blames geolocator anyway, ignore it). **Every path that starts location updates goes through `ensureLocationPermission()`** (`location_helper.dart`) — `_startListener`, `_startNewTransect`, `goToCurrentLocation`. The plugin's `changeSettings` starts native updates immediately, and doing that without `ACCESS_FINE_LOCATION` was a `SecurityException` thrown in a GMS callback that nothing in Dart could catch (start transect, or "Continue" on the resume dialog, after declining the prompt). The gate is deliberately re-run every time, never cached: an "Only this time" grant expires in the background and the user can revoke in settings; `location` 10 also turns that SecurityException into a `PERMISSION_DENIED` error, which is why it was upgraded. `grantedLimited` (Android 12+ "Approximate", iOS reduced accuracy) is treated as not enough. On Android the upgrade-to-precise dialog appears only for a request of `ACCESS_FINE_LOCATION` **alone** — the plugin's `requestPermission` returns at once because coarse already counts as granted — so it goes over the MainActivity channel (`requestPrecisePermission`); iOS has no prompt for it, only Settings. `_startTransect` and `_startListener` each keep their in-flight future and hand it to a second caller: the subscription is assigned only after several awaits, and a double tap on Start used to open two transect rows and leak a subscription that kept recording after Stop. The startup permission flow and the "unfinished transect" dialog are **sequenced** (`_goToCurrentLocation().whenComplete(_checkOpenTransect)`) so two permission requests are never in flight. The permission flow: a custom pre-permission dialog (`showPermissionInfoDialog`) precedes the system prompt. **Background mode is tied to recording**: `_startListener` calls `enableBackgroundMode()` (rationale → "Allow all the time" → plugin foreground service) and `_stopListener` — the single exit for pause, stop and clear — calls `disableBackgroundMode()`. It used to be switched on from `goToCurrentLocation`, i.e. on every launch and my-location tap, and never off, so the Android foreground service and its notification kept tracking with no transect in progress. The my-location button therefore no longer stops and restarts the stream either. The dialog text is **platform-specific** (`Platform.isIOS` in ux_builder.dart) because Android needs a two-step "Allow all the time" grant while iOS does not. That second step is **not** the plugin's: `location`'s own `enableBackgroundMode` calls `requestPermissions([ACCESS_FINE_LOCATION, ACCESS_BACKGROUND_LOCATION])` in one go, and Android 11+ ignores any request that bundles background with foreground — no prompt, nothing granted, which is exactly how the "Allow all the time" step went missing. `ACCESS_BACKGROUND_LOCATION` is therefore requested alone, after the foreground grant, over a MethodChannel in `MainActivity.kt` wrapped by `lib/utils/background_location_permission.dart`; `ensureBackgroundPermission()` in location_helper runs it (rationale dialog → request → settings fallback) before handing off to the plugin, which then only starts its foreground service. It asks **once per app run** — a user who declined should not be re-prompted on every transect start. On Android 11+ the request opens the app's location settings page instead of a dialog and returns empty `grantResults`, so the callback answers from a fresh `checkSelfPermission`, never from the result array. iOS keeps the plugin's flow: every channel call short-circuits to success there.

## Localization — keep three places in sync

1. **App strings**: easy_localization with `assets/translations/en.json` and `sr-Latn.json`; supported locales `en` and `sr-Latn`, fallback `en` (`lib/main.dart`). Any new UI string needs a key in **both** JSON files. This includes anything data-driven: a new species needs a `species.<latin>` entry **with any dots stripped from the key** (see `speciesKey()`), a new enum value needs one under its block (`stage`, `sex`, `data_type`, `method`, `habitat`, `water_bed`), and a new export column needs one under `csv_header` (that block is deliberately not named `csv` — a block and a plain key cannot share a name, and `csv` is the label of the share button in the history sheet; `.tr()` on a block key throws a Map cast error at build time).
2. **iOS permission strings**: `ios/Runner/Info.plist` holds the English (default) `NSLocation*UsageDescription`, `NSCameraUsageDescription`, `NSPhotoLibraryAddUsageDescription` and `NSPhotoLibraryUsageDescription` values; localized overrides live in `ios/Runner/{en,sr-Latn,sr}.lproj/InfoPlist.strings` (registered as a variant group in project.pbxproj). If a permission string changes, update the plist **and all three** .strings files — Apple rejected the app once (Guideline 4) for permission prompts not matching the app's language.
3. **Android**: permission dialogs are system-provided; no strings to maintain.

A `.strings` value must not contain a raw `"` — Xcode fails the build with "Couldn't parse property list", pointing at line 0 of the file.

## Media permissions

Photos deliberately cost **no** sensitive permission. On Android `image_picker` takes photos through `ACTION_IMAGE_CAPTURE` (so no `CAMERA` — declaring it would only make Android start demanding it) and picks through the Android 13+ photo picker (so no `READ_MEDIA_IMAGES`, which Play does gate behind a declaration form). The manifest carries only `WRITE_EXTERNAL_STORAGE` with `android:maxSdkVersion="29"` plus `android:requestLegacyExternalStorage="true"`, both required by `gal` below API 29; capped that low it does not trigger Play's storage declaration, which targets `MANAGE_EXTERNAL_STORAGE`. What does need updating before a release is the **Play Data safety form** ("Photos and videos" — not collected, not shared, since nothing leaves the device except through the user's own share sheet) and the privacy policy behind `PRIVACY_POLICY_URL`.

On iOS the three usage descriptions above are mandatory or the build is rejected outright (ITMS-90683); `NSPhotoLibraryUsageDescription` is needed on top of the add-only one because `gal` writes into a *named* album. The App Privacy label stays "Data not collected" — Apple does not count on-device-only data as collected.
