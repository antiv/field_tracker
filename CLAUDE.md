# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A pub workspace holding the field-survey tracker apps and the package they share. A tracker records "transects" (survey routes) on a Google Map, drops points with observation records, attaches photos to a record, and exports/shares as CSV/KML/KMZ. Android and iOS.

- `packages/tracker_core` — everything the apps share: the map screen, GPS recording, photos, sembast storage, zip backup, CSV/KML/KMZ, the drawer, the record form shell, the UI translations.
- `packages/tracker_location_permission` — a Flutter plugin (Android only) with the one-permission-at-a-time location requests; the apps' `MainActivity.kt` is the plain `FlutterActivity`.
- `apps/bird_tracker` — Bird Tracker (`rs.antonijevic.bird_tracker` / `rs.antonijevic.birdTracker`).
- `apps/herp_tracker` — Herp Tracker, reptiles and amphibians (`rs.antonijevic.herp_tracker` / `rs.antonijevic.herpTracker`).
- `apps/ciconia_tracker` — Popis roda, white stork nest census (`rs.antonijevic.ciconia_tracker` / `rs.antonijevic.ciconiaTracker`). Not yet published.

Each app has its own `CLAUDE.md` with only its domain. The three apps started as copies of each other; the shared history stops at the monorepo — there is no data migration between them, though a KML exported by one imports into another (see KML below).

## Commands

Flutter is managed by **fvm** — plain `flutter` is not on PATH. Use `fvm flutter ...`.

```bash
fvm flutter pub get             # anywhere in the workspace: resolves every member, one pubspec.lock at the root
tool/check_all.sh               # analyze + test for the core and every app — a core change is done when this is green
cd apps/bird_tracker && fvm flutter run          # dev run of one app on a connected device
cd apps/bird_tracker && fvm flutter analyze      # one member
cd apps/bird_tracker && fvm flutter build ios --no-codesign
```

CI (`.github/workflows/ci.yml`) runs `tool/check_all.sh` on every PR. The workspace pins **one version of every dependency** for all members; `flutter analyze` fails on `info`-level lints too, so the check script is strict by nature.

Tests: `packages/tracker_core/test` holds the contract (`contract_test.dart`: KML payload under any namespace, CSV columns and RFC 4180 quoting, translation merging, the form shell with and without a species field) and the archives (`media_archive_test.dart`: KMZ, backup zip, photo sweep) against a minimal `TestRecord` (`test/test_config.dart`). Each app's `test/` holds its export contract and its form. Widget tests pump `localizedTestApp()` from `package:tracker_core/testing.dart` inside `tester.runAsync` — without that the translations never load and every `.tr()` comes back as the raw key — after `SharedPreferences.setMockInitialValues({})`, `EasyLocalization.ensureInitialized()` and `TrackerConfig.current = <app config>` in `setUpAll`.

Three things bite when testing anything photo-related: `dart:io` futures never resolve inside `testWidgets`' fake async, so a temp media directory has to be created in `setUp`/`setUpAll` and `MediaService().init(root: …)` pointed at it; an `Image.file` whose file actually exists starts an image decode the test binding only finishes inside `runAsync`, so `pumpAndSettle` hangs forever if a thumbnail resolves; and the photo strip pushes the form's buttons past the default 800×600 viewport, so a tap on Save needs an `ensureVisible` first.

### Release builds — per app, from the app directory

Every app is a complete Flutter project: its own `pubspec.yaml` (name, `X.Y.Z+N` version, assets), `android/`, `ios/`, `.env`, scripts. `tracker_core` has no version of its own; when it changes, every app is released on its own schedule with its own bump.

- **Android**: `cd apps/<app> && ./build_release.sh [--bump] [--upload]` — cleans, builds obfuscated appbundle, copies to `<app name>.aab` in the app directory. `--bump` increments patch+build in pubspec. `--upload` then pushes the bundle to the Play **internal** track (`PLAY_TRACK` in `android/deploy.env` overrides) through `tool/play_upload.py`, one Play Developer API edit driven by a service account key — needs `python3` with `google-api-python-client`; every precondition is checked before the bump and the build. The API cannot make an app's *first* upload — Play insists that one goes through the console by hand (ciconia still needs it). The upload is not per app: the same script and the same service account serve all three.
- **iOS**: `cd apps/<app> && ./deploy_ios.sh` — full build + signed export + upload to App Store Connect via API key. **Bumps version by default**; use `--no-bump` if the version was already bumped, `--no-upload` to only produce the .ipa. Requires `ios/deploy.env` (see `ios/deploy.env.example`). The script patches the generated SPM `Package.swift` from iOS 13 → 15 (the project minimum; file_picker alone needs 14) before building — don't "fix" that seemingly redundant sed. The export options differ per app (bird: manual profile, herp: automatic) — that is per-app configuration, not drift.

Apple requires a new build number for every App Store Connect upload.

- **Toolchain**: Flutter is pinned in `.fvmrc` (3.47.5); CI follows `stable`. The Android shells sit on the Flutter template versions (Gradle 9.3.1 / AGP 9.1.0 / Kotlin 2.4.0, `android.builtInKotlin=false` and `android.newDsl=false` in `gradle.properties` as the template sets them). AGP 9 refuses `proguard-android.txt`, so the release build uses `proguard-android-optimize.txt`. Do not bring back the old `subprojects { compileSdk = 34 }` block in `android/build.gradle.kts` — it dragged every plugin down to 34 and broke as soon as one pulled in `androidx.core` 1.18. `tracker_location_permission` no longer applies the Kotlin Gradle plugin (built-in Kotlin); `location` still does, which is the one KGP warning left and not ours to fix. iOS runs the **UIScene** lifecycle: `AppDelegate` adopts `FlutterImplicitEngineDelegate` and registers the plugins in `didInitializeImplicitFlutterEngine`, `Info.plist` carries `UIApplicationSceneManifest` — the Maps key must still be handed to `GMSServices` before `super.application(...)`. `google_maps_flutter_ios_sdk9` adopts Swift Package Manager for iOS 15+. The gen_snapshot "unobfuscated DWARF" warning on Android is expected: the tool leaves stripping to AGP.

## Configuration / secrets (not in git, per app)

- **`apps/<app>/.env`** — bundled as a Flutter asset and required at runtime (`runTrackerApp` crashes without it). Keys: `MAPS_API_KEY` (+ optional `MAPS_API_KEY_ANDROID` / `MAPS_API_KEY_IOS` overrides), `PRIVACY_POLICY_URL`. Maps keys are restricted per package/bundle, so each app needs its own file. Consumed in three places: Dart via flutter_dotenv, Android via `build.gradle.kts` → manifest placeholder `${mapsApiKey}`, iOS via `AppDelegate.swift` which parses the bundled asset at runtime. CI creates an empty one.
- **`apps/<app>/android/key.properties`** — release keystore config for Android signing.
- **`apps/<app>/ios/deploy.env`** — App Store Connect API key credentials for deploy_ios.sh.
- **`apps/<app>/android/deploy.env`** — `PLAY_SERVICE_ACCOUNT_JSON`, the path to the service account key for `build_release.sh --upload` (see `android/deploy.env.example` for the one-time Cloud Console / Play Console setup). The key itself lives outside the repo.

## Architecture

An app is a `TrackerConfig` (`packages/tracker_core/lib/config/tracker_config.dart`) and one call: `runTrackerApp(config)`. The config carries the branding (title, logo, gallery album, photo file prefix, db name, backup name, KML namespace) and the domain hooks:

- **`TrackerRecord`** — what the core knows about a record: `species`, `photos`, `toJson`, `summary` (one line: the KML description) and `subtitle` (the line under the species in the point's list). The app's record class implements it; `recordFromJson` is its inverse. `Placemark.records` is a `List<TrackerRecord>` persisted under the JSON key **`species`** — that is what every stored transect, backup and KML payload already uses, do not rename it.
- **Form** — `RecordFormShell` (core) owns the species autocomplete, the `PhotoStrip` with its file rules, validation feedback and the Cancel / Save and new / Save buttons. The app's `recordFields` builder returns a `StatefulWidget` whose state extends `RecordFieldsState`: `collect(species:, existing:)` builds the record after the shell's `Form` validated, `reset()` is "save and new". The shell hands the fields the photo strip so they decide where it sits (herp puts it before the Advanced section, bird at the end). `speciesCatalog: null` removes the species field (a single-species app); `singleRecordPerPoint: true` removes "Save and new" and the point sheet's add button once the point has its record.
- **Export** — `exportColumnLabels()` and `exportValues(point, record)` are the record's columns, in order, called at export time so labels follow the app language. Core adds transect name, point number and photo names after them. That one list drives both the CSV (`Transect.toCSV`, cells quoted per RFC 4180 by `Transect.csvCell`) and the `<Data>` rows a KML viewer shows in the balloon (numbered when a point holds several records).
- **Legacy description parser** — `recordsFromLegacyDescription` reads records back out of a KML placemark's prose `<description>` when there is no payload. Only bird ever shipped such exports; the others leave it null.
- **Extra menu items** — `extraMenuItems` go into the drawer's configuration section (ciconia's surveyor details). App preferences go through `DataService().getString/setString`; the core does not know the keys.
- **Shared widgets** for the fields: `OptionPicker` (dropdown, or a searchable dialog for long lists, with a `labelOf` callback), `EnumRadio`, `CodePicker` (numbered codes with descriptions, e.g. atlas breeding codes), `CountField` (−/+), `BtAutocomplete`, `PhotoStrip`.

`TrackerConfig.current` is a static set by `runTrackerApp` (tests set it directly); it is what the core reads everywhere.

- **State**: `service/data_service.dart` — a ChangeNotifier **singleton** exposed through `provider`; holds the active `Transect`, map controller/completer, map type, and SharedPreferences accessors. Widgets call `DataService()` directly (factory returns the singleton) and `notify()` to trigger rebuilds.
- **Persistence**: `service/sembast_service.dart` — sembast NoSQL singleton with a single `transects` store, in `<documents>/<config.dbName>`. Models are **manually JSON-serialized** (`toJson`/`fromJson`, no codegen). A backup is a **`.zip`** (`utils/backup_utils.dart`): `<backupBaseName>.json` at the root — byte-identical to the old plain-JSON backup — plus `media/` with the record photos. It is written and read with `ZipFileEncoder` / `decodeStream`, streaming photo bytes straight between the media directory and the archive — never buffer a whole archive, a season of field photos is hundreds of megabytes. Restore still accepts a bare `.json` so older backups keep working, and it is destructive by design: it wipes the store and then sweeps media files no restored record references.
- **Models** (`model/`): `Transect` (route with start/end, name) → `points` (recorded track) + `markers` (`Placemark` points, each with `altitude`/`accuracy` off the GPS fix) → `records`. `Transect` owns the CSV export and the share entry points; `utils/kml_utils.dart` owns KML and `utils/kmz_utils.dart` the KMZ wrapper around it.
- **Export formats**: CSV is written as UTF-8 **with BOM** — species names and notes carry Serbian diacritics, and both exports used to go out through `.codeUnits`, which silently mangled them. KML carries the records as JSON in each placemark's `<ExtendedData>`; that payload, not the human-readable `<description>`, is what re-import reads, so any new record field round-trips as soon as it is in `toJson`. It sits in a **namespaced** element (`<bt:records>`, `<herp:records>`, `<ct:records>` — the app's `kmlNamespace`) because a plain `<Data name="records">` is what viewers render as a name/value table, and they would print the raw JSON at the user. Import matches the element **by local name whatever the namespace**, and still reads the pre-namespace plain `<Data name="records">`, so every KML already shared with a colleague, from any of the apps, still imports — as long as the receiving app's `recordFromJson` can read the record. `Transect.shareKML` emits a **KMZ** whenever a record photo is on disk and a plain `.kml` otherwise; a KMZ is a zip of `doc.kml` plus `files/`, and only then does `generateKML(photos: …)` swap the placemark description for CDATA HTML with `<img src="files/…">`. That argument is the exact list the archive bundles, so a record naming a photo whose file has gone missing keeps the name in `ExtendedData` — losing it would erase what was photographed — but gets no `<img>` and therefore no broken image in Google Earth. `Transect.hasPhotos` answers from memory alone because the history list calls it from an item builder every frame; `KMZUtils.availablePhotos` is the one that stats the disk, once, in `shareKML`. Import (`showImportDialog`) accepts both and decides which by **sniffing the zip magic**, never by the extension: share targets rename attachments freely. That subject and every export file name go through `sanitizeFileName` (`file_utils.dart`) — the transect name is free text and a `/` in it used to become a directory separator in the shared file's path, taking the extension with it. The picker uses `FileType.any` plus its own check rather than `FileType.custom`, because that maps extensions through Android's `MimeTypeMap`, which knows neither `kml` nor `kmz` and greys the files out. The `<img src="files/…">` balloon images only render in Google **Earth Pro** (desktop); the **web** builds of both Earth and My Maps parse the tags but never resolve a path into the archive, so photos read as broken there — nothing in the KMZ is wrong when that happens.
- **Photos** (`service/media_service.dart`, strip UI in `widgets/photo_strip.dart`): a record may carry several. Each one is stored twice — the canonical copy under `<appDocuments>/media`, which every thumbnail and every export reads, and a user-visible copy in the app's gallery album (`config.galleryAlbum`) via `gal`. A failed gallery write is not fatal, only the shortcut in Photos is lost. `TrackerRecord.photos` holds **file names, never paths** (`<photoPrefix>_<stamp>_<suffix>.jpg`): the iOS app container path changes between installs, so a persisted path would break. Photos hit the disk before the record exists, so `RecordFormShell` reconciles on save (files it no longer lists are deleted) and on dispose (files added and then abandoned are deleted) — never at the moment the user taps the ×, or cancelling would gut a saved record. `_clear()`, the "save and new" path, resets both lists so the next record cannot delete the previous one's files. The gallery copy is never deleted, the way a camera app behaves.
- **Deleting photos**: only the form deletes files on its own, and only ones no saved record ever owned. Deleting a transect, a point or a record goes through `showDeleteWithPhotosDialog` (`ux_builder.dart`), which adds an opt-in checkbox — **off by default** — for the photos that delete would orphan; without it the files stay. The checkbox copy says photos taken in the app survive in the gallery album but imported ones do not, and that is literally true: `MediaService.writeBytes`, the path a KMZ import and a backup restore take, never pushes to the gallery. Restore is the one place that still sweeps photos without asking, which is in character since it replaces the whole database anyway.
- **Map camera**: the camera follows the user only while the app is `resumed` (`_appVisible`, from `WidgetsBindingObserver` in `home_page.dart`); points are still recorded and drawn on the next resume. Updates keep arriving every second from the foreground service with the screen off, and animating the paused, surface-less MapView on each one fed the Maps renderer NaN targets — `IllegalArgumentException: NaN is not a valid value: (NaN,NaN)` on the render thread, uncatchable from Dart because it is not thrown inside a Pigeon handler. `_followCamera` also skips a repeat of the last target (distanceFilter is 0) and any non-finite zoom or coordinate. Coordinates are validated on every way in (`geo_utils.dart`: `isFiniteLatLng`, `finiteOrNull`): `double.parse('NaN')` succeeds in Dart, so KML import, `Point.fromJson`/`Placemark.fromJson` and `goToFirst` drop what the map could not place instead of handing it over.
- **UI helpers**: `utils/ux_builder.dart` — global dialogs/snackbars/bottom sheets using `context_holder` (`ContextHolder.currentContext`), so no BuildContext threading. All user-facing strings go through easy_localization `.tr()`; strings that name the app carry `{app}` and are called with `namedArgs: appArgs`.
- **Location**: uses the `location` package (10.x — not geolocator/permission_handler; Play Console's crash "SDK provider note" blames geolocator anyway, ignore it). **Every path that starts location updates goes through `ensureLocationPermission()`** (`location_helper.dart`) — `_startListener`, `_startNewTransect`, `goToCurrentLocation`. The plugin's `changeSettings` starts native updates immediately, and doing that without `ACCESS_FINE_LOCATION` was a `SecurityException` thrown in a GMS callback that nothing in Dart could catch — the top production crash of Bird Tracker 1.0.16 (start transect, or "Continue" on the resume dialog, after declining the prompt). The gate is deliberately re-run every time, never cached: an "Only this time" grant expires in the background and the user can revoke in settings; `location` 10 also turns that SecurityException into a `PERMISSION_DENIED` error, which is why it was upgraded. `grantedLimited` (Android 12+ "Approximate", iOS reduced accuracy) is treated as not enough. On Android the upgrade-to-precise dialog appears only for a request of `ACCESS_FINE_LOCATION` **alone** — the plugin's `requestPermission` returns at once because coarse already counts as granted — so it goes over the MainActivity channel (`requestPrecisePermission`); iOS has no prompt for it, only Settings. `_startTransect` and `_startListener` each keep their in-flight future and hand it to a second caller: the subscription is assigned only after several awaits, and a double tap on Start used to open two transect rows and leak a subscription that kept recording after Stop. The startup permission flow and the "unfinished transect" dialog are **sequenced** (`_goToCurrentLocation().whenComplete(_checkOpenTransect)`) so two permission requests are never in flight. The permission flow: a custom pre-permission dialog (`showPermissionInfoDialog`) precedes the system prompt. **Background mode is tied to recording**: `_startListener` calls `enableBackgroundMode()` (rationale → "Allow all the time" → plugin foreground service) and `_stopListener` — the single exit for pause, stop and clear — calls `disableBackgroundMode()`. It used to be switched on from `goToCurrentLocation`, i.e. on every launch and my-location tap, and never off, so the Android foreground service and its notification kept tracking with no transect in progress. The my-location button therefore no longer stops and restarts the stream either. The dialog text is **platform-specific** (`Platform.isIOS` in ux_builder.dart) because Android needs a two-step "Allow all the time" grant while iOS does not. That second step is **not** the plugin's: `location`'s own `enableBackgroundMode` calls `requestPermissions([ACCESS_FINE_LOCATION, ACCESS_BACKGROUND_LOCATION])` in one go, and Android 11+ ignores any request that bundles background with foreground — no prompt, nothing granted, which is exactly how the "Allow all the time" step went missing. `ACCESS_BACKGROUND_LOCATION` is therefore requested alone, after the foreground grant, over the `rs.antonijevic.tracker/background_location` MethodChannel of the **`tracker_location_permission` plugin** (`packages/tracker_location_permission`: a `FlutterPlugin` + `ActivityAware` + `RequestPermissionsResultListener`, Android only — the Dart `BackgroundLocationPermission` short-circuits to success elsewhere, so the plugin declares no iOS platform at all; its Gradle file pins no AGP/Kotlin version, the app's apply); `ensureBackgroundPermission()` in location_helper runs it (rationale dialog → request → settings fallback) before handing off to the plugin, which then only starts its foreground service. It asks **once per app run** — a user who declined should not be re-prompted on every transect start. On Android 11+ the request opens the app's location settings page instead of a dialog and returns empty `grantResults`, so the callback answers from a fresh `checkSelfPermission`, never from the result array. iOS keeps the plugin's flow: every channel call short-circuits to success there.

## Localization — keep three places in sync

1. **App strings**: easy_localization, supported locales `en` and `sr-Latn`, fallback `en` (`kSupportedLocales` in `app/tracker_app.dart`). Two files feed each locale through `MergedAssetLoader`: `packages/tracker_core/assets/translations/<locale>.json` (the UI) first, then `apps/<app>/assets/translations/<locale>.json` on top — the app's value wins on a key both define, nested blocks (`species`, `csv_header`) merge key by key. So the core holds every shared string once, with generic defaults for the few that read differently per domain (`species_title` "Records", `add_species_btn`, `about_description`, the location-permission prose), and an app overrides only what it wants worded its way and adds its domain (species names, field labels, option labels, CSV headers). A new UI string goes into **both core JSON files**; a new domain string into both of the app's. **No dots in keys**: easy_localization reads a dot as a path separator, so a species name like `Anas sp.` came back as the raw key. Each app maps a Latin name to its key through `config.speciesTranslationKey` (bird: dot → underscore, herp: dot dropped); the Latin names in the catalog keep their dots — they are what records and exports carry. Each app's form test checks that every catalog name (or option) resolves in both locales.
2. **iOS permission strings**: `apps/<app>/ios/Runner/Info.plist` holds the English (default) `NSLocation*UsageDescription`, `NSCameraUsageDescription`, `NSPhotoLibraryAddUsageDescription` and `NSPhotoLibraryUsageDescription` values; localized overrides live in `ios/Runner/{en,sr-Latn,sr}.lproj/InfoPlist.strings` (registered as a variant group in project.pbxproj). If a permission string changes, update the plist **and all three** .strings files — Apple rejected an app once (Guideline 4) for permission prompts not matching the app's language.
3. **Android**: permission dialogs are system-provided; no strings to maintain.

A `.strings` value must not contain a raw `"` — Xcode fails the build with "Couldn't parse property list", pointing at line 0 of the file.

## Media permissions

Photos deliberately cost **no** sensitive permission. On Android `image_picker` takes photos through `ACTION_IMAGE_CAPTURE` (so no `CAMERA` — declaring it would only make Android start demanding it) and picks through the Android 13+ photo picker (so no `READ_MEDIA_IMAGES`, which Play does gate behind a declaration form). The manifest carries only `WRITE_EXTERNAL_STORAGE` with `android:maxSdkVersion="29"` plus `android:requestLegacyExternalStorage="true"`, both required by `gal` below API 29; capped that low it does not trigger Play's storage declaration, which targets `MANAGE_EXTERNAL_STORAGE`. What does need updating before a release is the **Play Data safety form** ("Photos and videos" — not collected, not shared, since nothing leaves the device except through the user's own share sheet) and the privacy policy behind `PRIVACY_POLICY_URL`.

On iOS the three usage descriptions above are mandatory or the build is rejected outright (ITMS-90683); `NSPhotoLibraryUsageDescription` is needed on top of the add-only one because `gal` writes into a *named* album. The App Privacy label stays "Data not collected" — Apple does not count on-device-only data as collected.

## Adding a tracker app

`apps/<name>/` = `lib/main.dart` (`runTrackerApp(config)`), `lib/domain/` (the record implementing `TrackerRecord`, the config, the form fields), `lib/configuration/` (catalog, option enums), `assets/translations/{en,sr-Latn}.json` with the domain keys, `assets/icons/logo.svg`, `android/` and `ios/` shells (copy an existing app's and rename the package, bundle id, display name, permission prose and icons — `ciconia_tracker` was made that way), `.env`, `pubspec.yaml` with `resolution: workspace` and a path dependency on `tracker_core`, and a line in the root `pubspec.yaml` `workspace:` list. Nothing in the core needs to change.
